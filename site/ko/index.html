인덱스로 훨씬 빠르게

rg, fd, ast-grep, cat, sed를 이어 붙여 쓰던 걸 바이너리 하나로 끝냅니다. 모든 명령이 같은 인덱스, 같은 줄 번호를 씁니다. 결과는 늘 최신이고, 에이전트 둘이 같은 파일을 고쳐도 한쪽 수정이 몰래 사라지지 않습니다.

출력은 ripgrep과 바이트까지 동일 Tree-sitter 24개 언어 PDF · 오피스 · HWP · 압축파일 MIT / Apache-2.0

기능

    
에이전트가 코드에 하는 일, 전부.

    

      

        

        
빠른데 낡지 않음

        
트라이그램 인덱스로 후보만 고르고, 후보는 전체 스캔과 똑같은 기준으로 다시 확인합니다. 인덱싱 뒤에 바뀐 파일은 mtime/size/ctime/inode로 알아채서 바로 스캔합니다. 데몬은 필요 없습니다.

      

      

        

        
ripgrep 그대로

        
lancet rg는 ripgrep 플래그를 그대로 받고 출력도 똑같습니다. 코드베이스 8개에서 바이트 단위로 비교해 봤습니다. .gitignore, .rgignore, glob, --type도 같은 규칙으로 처리합니다.

      

      

        

        
구조 검색·치환

        
lancet ast '$X.unwrap()' --rewrite '$X?'를 Tree-sitter 24개 언어에서 씁니다. $$$ARGS, 문장 메타변수도 됩니다. --apply를 붙이기 전엔 diff만 보여 줍니다.

      

      

        

        
필요한 만큼만 읽기

        
read --symbol, 줄 범위, PDF 페이지, 시트 셀까지 토큰 예산 안에서 읽습니다. 같은 걸 찾을 때 파일을 통째로 읽는 것보다 컨텍스트가 5–30배 적게 들었습니다.

      

      

        

        
여럿이 동시에 고쳐도 안전

        
edit, patch, AST 치환 모두 같은 잠금 + compare-and-swap으로 씁니다. --rev가 옛날 거면 conflict를 돌려주고 한 바이트도 안 씁니다. 심볼릭 링크·하드 링크·권한은 그대로 두고, 구문 오류가 늘어나는 수정은 거절합니다.

      

      

        

        
문서도 같은 방식으로

        
PDF, DOCX, PPTX, XLSX, HWP, EPUB, ZIP, TAR를 외부 도구 없이 직접 풉니다(압축 폭탄 상한 있음). .docx에서 42번째 줄로 찾은 건 read에서도 42번째 줄입니다.

      

    

  






  

    
벤치마크

    
코드베이스 8개, 언어 7개. 출력은 ripgrep과 똑같이.

    
잘 안 나오는 문자열을 찾을 때 ripgrep보다 몇 배 빠른지입니다. auto는 매번 최신인지 확인하는 기본 모드, trust는 인덱스만 믿고 답하는 모드(--trust-index)입니다. 텍스트 결과는 전부 ripgrep 출력과 바이트 단위로 맞춰 봤습니다.


    

      

        
ripgrep보다 몇 배 빠른가 (로그 축, 쿼리별 최소–최대)

        
auto (항상 최신)trust (--trust-index)

코드베이스파일인덱스 빌드 · 크기auto 대 rgtrust 대 rgAST 대 ast-grep

          
        

      

    

    
느린 경우도 있습니다. 리터럴이 하나도 없는 정규식은 인덱스로 좁힐 수가 없어서 ripgrep과 비슷하거나 최대 1.4배 느립니다. 리터럴 없는 AST 패턴은 ast-grep의 0.6–1.0배입니다. 전체 표와 측정 방법 →

  






  

    
왜 도구 하나인가

    
도구를 이어 붙이면 이음새에서 터집니다.

    
아래는 전부 실제 도구로 재현한 결과입니다: bench/failure_modes.py.

    

      
이렇게 하면실제로 벌어진 일lancet

      
        
rg -n → sed -i 편집 두 번두 번째 편집이 엉뚱한 줄을 고침. 둘 다 종료 코드 0edit --edits는 처음 읽은 줄 번호 기준

        
에이전트 4개: 읽기 → 수정 → 다시 쓰기업데이트 800개 중 600개가 소리 없이 사라짐edit --rev: 800개 중 0개 유실

        
낡은 hunk가 섞인 patch -p1한 파일은 바뀌고 한 파일은 거부. 반쯤 적용된 상태patch: 하나도 안 쓰고 conflict

        
sed로 이름 변경주석, 문자열까지 바뀜 (0.3–11.7%)refs / ast는 코드만 건드림

        
.docx에 rga → pandoc읽어 온 줄 40개 중 0개에 검색어가 있음40개 중 40개. 검색과 읽기가 같은 추출 결과를 씀

        
파일 20개 수정 직후의 zoekt새로 쓴 내용은 0개 파일에서 찾고, 지운 내용은 20개 파일에서 계속 나옴auto 모드: 20과 0

        
sed -i / perl -pi하드 링크, 심볼릭 링크가 깨지고 권한 0640도 날아감링크·권한·소유자 그대로

2. 검색:  lancet rg -w SYMBOL src  |  lancet 'query in ext:rs'
3. 읽기:  lancet read FILE --symbol NAME --json   # "rev" 기억
4. 수정:  lancet edit FILE --find '...' --with '...' --rev REV --apply
5. conflict(종료 코드 2): 다시 읽고 새 내용에 적용한 뒤 새 rev로 재시도.
